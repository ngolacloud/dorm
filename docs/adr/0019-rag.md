# ADR 0019 — RAG: automatic pgvector indexing and semantic/hybrid search as an optional crate

Status: proposed · 2026-11-01 · extends the two-front-ends design (ARCHITECTURE.md)
and the observability brick ([ADR 0008](0008-observability.md)); depends on the
dialect/driver seam ([ADR 0002](0002-multi-backend.md), [ADR 0003](0003-backend-generic-db.md)).

## Context

A DORM model is a `&'static ModelMeta` the whole system reads — the typed API,
the dynamic REPL, the migrator and Studio all converge on it. That single
description is what lets one compiler serve every front end safely: no identifier
comes from a caller, no value is formatted into SQL. The ask here is to let a
model opt into **semantic and hybrid retrieval** — "find the tickets about email
after the migration" — without weakening either invariant and without pretending
that a vector search is exempt from the tenant filter every other query obeys.

Three forces shape the decision:

1. **No new weight for people who do not use it.** A crate that only defines
   models depends on `dorm-core` alone. Adding RAG must not add a transitive
   `pgvector`/`fastembed`/HTTP-client edge to `dorm-core`'s graph, nor change
   `ModelMeta`. `FieldType`, `Value`, `ModelMeta` and `FieldMeta` are public and
   not `#[non_exhaustive]`; this ADR adds **no variant and no field** to any of
   them (the brief's hard constraint, which the acceptance tests pin).
2. **The same safety, including the tenant.** A semantic search is still a query.
   Its filters — above all a `tenant_scoped` model's tenant — must apply *before*
   similarity ranking, through the existing compiler and registry, never through
   SQL written by hand next to a vector literal.
3. **Indexing must survive every write path.** Rows are written through the typed
   `QuerySet`, through the REPL's `insert`/`:raw`, through `dorm db execute
   --write`, through Studio, through `db seed`, and straight through `psql`. An
   index that only sees the typed path is wrong the moment an operator runs one
   `UPDATE` by hand.

## Decision

Ship RAG as a **new, optional crate `dorm-rag`** that depends on `dorm-core` but
that `dorm-core` never depends on. A model opts in with a separate derive; the
index lives in shadow tables the migrator owns; change capture is a **database
trigger**, not a QuerySet hook; and search is an **extension trait** over the
existing `QuerySet` plus a dynamic entry point for the REPL and MCP. Each of
those is a deliberate seam, taken in turn below.

### `#[derive(Rag)]` with an `#[rag(..)]` attribute — not a `rag` feature on `#[derive(Model)]`

A model declares RAG next to its `Model` derive:

```rust
#[derive(Model, Rag, Debug, Clone)]
#[model(table = "tickets", tenant_scoped)]
#[rag(
    fields   = ["title", "body"],
    template = "{title}\n\n{body}",
    embedder = "default",
    chunk_size = 800,
    chunk_overlap = 100,
    metadata = ["status"],
    distance = "cosine",
)]
pub struct Ticket { /* … */ }
```

`#[derive(Rag)]` emits one `&'static RagMeta`, submitted into a distributed slice
**that `dorm-rag` owns** (`inventory::collect!(RagMeta)` inside `dorm-rag`), keyed
to the model by its registered name. `ModelMeta` does not change and the `Model`
derive does not change: a RAG model is a model that *also* carries a second,
independent static, exactly as the two front ends are two readers of one
description. The derive macro itself lives in `dorm-derive` behind a **non-default
`rag` feature** and is re-exported as `dorm_rag::Rag`, so it reuses the existing
field-parsing helpers and the single compile-time story rather than starting a
fourth proc-macro crate.

The alternative — a `rag` feature on `#[derive(Model)]` that teaches the *Model*
derive to read `#[rag(..)]` and emit a `RagMeta` — was rejected on three counts.
It would make the `Model` derive name `::dorm_rag::…` paths, coupling the two
even for the build where the feature is off (a feature changes what a crate emits,
not whether the code exists). It would route a second, orthogonal concern through
the one macro whose output every model already depends on, so a bug in RAG
emission could break a plain model. And it blurs the opt-in: a reader sees
`#[derive(Model, Rag)]` and knows precisely which models are indexed, whereas a
feature flag is invisible at the call site. A separate derive keeps RAG *additive
and legible* — the same reason `save`/`delete` are instance methods on the
`Model` impl and not baked into `ModelMeta`.

`RagMeta` is the RAG analogue of `ModelMeta`: all `&'static`, a closed shape, and
**not** `#[non_exhaustive]` only because `dorm-rag` is pre-1.0 and owns it alone;
it carries the model name, the source field list, the document template, the
embedder id, chunk sizing, the filterable metadata columns, and the distance
metric. It never holds a type parameter, so a `RagMeta` for a model defined in
another crate still resolves by name through the registry — the same decoupling
that lets two `#[derive(Model)]`s compile in any order.

### `dorm.schema`: `@@rag(..)` is a block attribute the generator compiles

The declarative schema gains a block-level attribute:

```prisma
model Ticket {
  id    Int    @id @default(autoincrement())
  title String @db.VarChar(200)
  body  String @db.Text
  @@rag(fields: [title, body], embedder: "default", metadata: [status])
}
```

`dorm generate` compiles `@@rag(..)` into `#[derive(Model, Rag)]` + `#[rag(..)]`
on the generated struct and adds a single `use dorm_rag::Rag;` import **only when
some model carries it** — a schema with no `@@rag` generates byte-for-byte what it
does today and pulls in no `dorm-rag` dependency. `dorm format` already preserves
unknown `@@…` lines verbatim (it formats text, not the AST — [the format brick]),
so `@@rag(..)` survives a format round-trip; a test pins that. The parser learns
the attribute so the generator and `dorm validate` can act on it rather than
skip it.

### `dorm validate` checks RAG at two levels, both without a running database

- **Schema level, in `dorm-schema` (`dorm generate` and `dorm validate`).** A new
  pure `dorm_schema::validate(&Schema)` checks, per model carrying `@@rag`: every
  `fields` entry names a declared scalar field **of type `String`** (text is the
  only thing an embedder can read), every `metadata` entry names a declared
  scalar field (so it can become a filterable shadow column), and the model has a
  primary key (so a chunk can be tied to its row). This runs at generate time —
  no project build, no DB — so a typo in `@@rag(fields: [titel])` fails before any
  SQL is written. `dorm validate` runs this pass first, reporting issues with the
  same `error`/`warning` severities and exit code `3` as the registry checks.
- **Registry level, in `dorm-rag` (`dorm_rag::validate()`), for hand-written
  models.** A model written in Rust bypasses the schema, so `dorm-rag` cross-checks
  each `RagMeta` against the live `ModelMeta` in the registry: the named model
  exists, each `fields`/`metadata` entry is a real column, each `fields` column is
  `FieldType::Text`, and the model has a primary key. The pure core of this
  (`validate_against(&[&RagMeta], &[&ModelMeta])`) is unit-tested; the project's
  generated `validate` binary calls it when it links `dorm-rag`.

## Storage and migrations (brick 2)

For each RAG model `tickets`, the migrator emits a **shadow table**
`dorm_rag_tickets`:

| column | purpose |
|---|---|
| `record_pk` | the row's primary key (typed to match the model's PK) |
| `tenant` | present **iff** the model is `tenant_scoped`; the pre-filter column |
| `chunk_index` | 0-based position of the chunk within the document |
| `content` | the chunk text |
| `embedding` | `vector(<dim>)` — dimension from the embedder |
| `content_hash` | hash of the chunk, so only changed chunks re-embed |
| `embedder` / `embedder_version` | which model produced the vector, for reindex |
| metadata columns | one per `metadata` entry, copied for pre-filtering |
| `created_at` / `updated_at` | `TIMESTAMPTZ` stamps |

plus a single **`dorm_rag_outbox`** (`model`, `record_pk`, `op`, `attempts`,
`last_error`, `enqueued_at`, `updated_at`). The generated DDL is reviewable in the
migration file and includes, in this order: `CREATE EXTENSION IF NOT EXISTS
vector`; the shadow tables; an **HNSW** index on `embedding` with the configured
metric (`vector_cosine_ops` by default); a **GIN** index on a `tsvector` of
`content` for the full-text half of hybrid search; and **`AFTER INSERT/UPDATE/
DELETE` triggers on the model table** that write `(model, pk, op)` into the outbox.
Removing `@@rag` generates the inverse migration (drop triggers, indexes, shadow
table — the extension is left, since other models may use it). This is wired into
`migrate make`/`dev`/`deploy` and `migrate diff`; the triggers are the one place a
RAG migration is not purely additive, and the diff shows them.

**Change capture is a trigger, by decision, not a QuerySet hook.** A trigger sees
every write — typed, `:raw`, `dorm db execute`, Studio, `db seed`, `psql` — so the
index cannot silently drift from the table, and the core write path is not touched
at all. The trigger enqueues *only* when a RAG `fields` or `metadata` column
actually changed (a `WHEN` clause comparing `OLD`/`NEW`), so an unrelated
`UPDATE` costs one predicate and no row. The cost is a row in the outbox per
relevant write and a worker to drain it (brick 3) — paid in exchange for an index
that is correct regardless of who wrote the data.

**SQLite is capability-detected, never faked.** With `@@rag` active on a SQLite
datasource, every RAG operation returns an explicit `Error` naming `sqlite-vec`
as the future path. There is no silent fallback to a non-vector search — that is
the ADR 0002 rule ("an unsupported capability returns an explicit error, never a
wrong result") applied to retrieval.

## Worker and embedders (brick 3 / 4)

`dorm_rag::worker::run(config)` and `dorm rag worker` drain the outbox in batches
with `SELECT … FOR UPDATE SKIP LOCKED`, so N workers run without stepping on each
other. Per event: load the row through the **dynamic** API (`fetch_value_rows`, so
the worker needs no compile-time knowledge of the model), render the template,
chunk it, diff chunk hashes against the shadow table (re-embed only what changed),
embed the changed chunks in one batch call, upsert, and delete now-orphaned
chunks; a delete event removes the row's chunks. Failures retry with exponential
backoff and dead-letter after N attempts; every step emits `tracing` on a
`dorm::rag` target in the ADR 0008 style (events, never a subscriber; never a
secret). Changing embedder or dimension marks the index stale and reindex is
incremental and online.

The `Embedder` trait is async, batched, and reports `dimension()` and
`model_id()`. Implementations sit behind features: `embed-local` (default, ONNX via
`fastembed`, so data never leaves the host), `embed-ollama`, and
`embed-openai-compat`. Configuration is `DELONIX_ORM_RAG_*`; keys are redacted in
logs exactly as `doctor` redacts a DSN password.

## Search (brick 5)

Typed, as an extension trait over `QuerySet<T>` so `dorm-core` is untouched:

```rust
let hits = Ticket::objects()
    .filter(ticket::status.eq("open"))
    .semantic("cliente sem acesso ao email depois da migração")
    .hybrid(0.7)        // vector weight; the rest is full-text; fused by RRF
    .min_score(0.35)
    .limit(10)
    .search().await?;   // Vec<Scored<Ticket>> { item, score, chunks }
```

Dynamic, for the REPL and MCP: `semantic_search(model, query, filters, opts) ->
Vec<ScoredRow>`, resolving everything through the registry.

**Pre-filtering is mandatory and reuses the compiler.** The `Plan`'s filters —
including the tenant for a `tenant_scoped` model — are compiled by the existing
`compile_select_on` into a subquery selecting the matching primary keys. That
subquery's `$n` placeholders are renumbered with the compiler's own
`shift_placeholders` (the same mechanism `compile_update` already uses to splice a
subquery after its `SET` parameters), and the vector is bound as a parameter with
a cast — `$k::vector` — so **no vector literal and no filter SQL is ever written
by hand, and the `Value` enum gains no variant**. The shadow search then ranks
only the pre-filtered pks. The generated search SQL (text and parameter order) is
pinned by snapshot tests alongside `sql_snapshots.rs`, and a live test proves a
`tenant_scoped` `search()` never returns another tenant's rows.

## Bricks (the order of work)

1. **Declaration** — `RagMeta`, `#[derive(Rag)]` (dorm-derive `rag` feature,
   re-exported by dorm-rag), `@@rag` in the schema parser/generator/formatter, and
   `dorm validate` (schema + registry). *This ADR's first increment.*
2. **Storage & migrations** — extension, shadow tables, `dorm_rag_outbox`, HNSW +
   GIN indexes, the enqueue triggers, and the reverse migration; wired into
   `migrate make/dev/deploy/diff`. SQLite capability error.
3. **Worker** — `dorm_rag::worker::run` and `dorm rag worker`: outbox drain with
   `SKIP LOCKED`, hash-diffed re-embedding, retries/dead-letter, tracing.
4. **Embedders** — the `Embedder` trait and `embed-local`/`embed-ollama`/
   `embed-openai-compat` behind features; `DELONIX_ORM_RAG_*` config with redaction.
5. **Search** — `RagQuerySetExt` (`semantic`/`hybrid`/`min_score`/`search`) and the
   dynamic `semantic_search`; compiler-reused pre-filtering; SQL snapshots; the
   tenant-isolation live test.
6. **CLI & REPL** — `dorm rag status|reindex|worker`; the REPL `search` verb and
   `:rag`.

## Consequences

- A crate that does not use RAG sees no change: `dorm-core`'s dependency graph is
  identical, `ModelMeta` is identical, and a schema with no `@@rag` generates the
  same bytes. The acceptance suite pins all three.
- Indexing is correct under every write path because the source of truth is a
  trigger on the table, not a hook in one client library. The price is an outbox
  and a worker, which also buys batching, retries and parallelism.
- A semantic search carries the same filters — and the same tenant isolation — as
  any other query, because it is pre-filtered through the one compiler, not beside
  it. Safety stays a property of construction.
- `embed-local` by default means the common case never ships text to a third party;
  the hosted embedders are an explicit, feature-gated choice.
- SQLite + RAG is an explicit, named error today, not a silent degrade — honest
  about what is and is not supported, per ADR 0002.

## What this is not

- **Not a change to `dorm-core`.** No new `Value` variant, no `FieldType`, no
  `ModelMeta` field. Search is an extension trait; the vector is a bound parameter
  with a cast.
- **Not a QuerySet hook.** Change capture is a database trigger, on purpose.
- **Not a silent SQLite fallback.** No pgvector means an explicit error.
- **Not a subscriber or a metrics exporter.** `dorm-rag` emits `tracing` events and
  leaves the sink to the binary, exactly as ADR 0008 does for `dorm::db`.
